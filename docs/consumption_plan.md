## 배경과 원칙

현재 INAZINA는 금융 경제만 있다. 은행, 주식, 채권, 옵션, 선물, ELS, 펀드, 복권, 환전이 있고, 돈이 실물로 나가는 소비처가 없다. 돈이 금융 안에서만 돌아 자산 가격과 대출이 부풀기 쉽다. 또한 M4 회계가 진행 중이라 원장 정합성이 가장 큰 제약이다.

1. **소비는 소각이 아니라 이전이다.** 구매자의 돈은 판매 법인(매출), 국고(세금), 플랫폼 법인(수수료)으로 나뉜다. 매출은 법인 이익과 배당 재원이 되고, 주가에는 아래 "매출–주가 상호작용"의 규칙으로 제한적으로 반영된다. 주가에 직접 연동한다고 약속하지 않는다.
2. **결제는 확정된 정산 규칙을 쓴다.** 상품 국적(통화)의 계좌가 있고 잔액이 충분하면 결제한다. 법인 판매자는 모든 화폐의 계좌를 가지므로(확정) 항상 해당 통화로 수령한다. 개인 판매자(중고거래)가 해당 통화 계좌가 없으면 `PayoutManager`의 환전/임시계좌 선택을 쓴다. 알림은 `NotificationManager`를 쓴다.
3. **공급은 한정하고 가격은 수급과 사건으로 움직인다.** 시장 사건(`market_events`)과 금리와 연결한다.
4. **한 번에 하나씩 낸다.** 공통 코어를 먼저 만들고 그 위에 얹는다.
5. **확률형 요소는 한도와 확률 공개를 기본 요구사항으로 한다.**

## 공통 코어: 소비 엔진

- 판매자(확정): 현존하는 법인(`company`)을 구조 변경 없이 그대로 판매자로 쓴다. 법인은 모든 화폐의 계좌를 가진다. 매출이 법인 원장에 전기되고 재무제표에 반영된다.
- 카탈로그: 상품, 가격 통화, 재고, 판매자, 카테고리.
- 주문: 결제 → 정산 → 완료/환불 상태 기계. 모든 단계를 저장점으로 묶어 부분 전기를 막는다.
- 세금: 국가별 부가가치세/소비세를 국고로 보낸다.
- 원장 연결: 모든 분개를 공통 전기에 연결하고 `reconcile_all_financial_ledgers`에 소비 대사 항목을 추가한다. 새 금액 필드는 금액 필드 레지스트리에 등록한다.
- 알림: 주문 완료, 배송, 임대료, 세금 납부를 벨로 보낸다.
- DB: SQLite와 PostgreSQL 스키마와 트리거를 함께 만든다.
- 테스트(확정): 모든 단계에서 SQLite/PostgreSQL 양쪽 테스트, 대사 0건 게이트, 확률 실측 통계 테스트를 시행한다.

## 아이템 시스템

출석, 뽑기, 강화, 쇼핑몰이 공유하는 새 자산 종류다.

- 아이템 정의: 종류(소모품, 장비, 재료, 수집품), 등급, 기본 능력치, 거래 가능 여부, 발행 총량 상한.
- 인벤토리: 유저별 수량과 개체별 속성(강화 단계, 내구도).
- 발행과 소멸: 모든 생성과 소멸을 이력으로 남긴다. 재료 소모와 파괴는 소각이 아니라 기록된 소멸이며 가치는 법인이나 국고로 이전한다.
- 거래: 유저 간 거래와 쇼핑몰 판매를 같은 카탈로그에 얹는다. 한정판은 여기서 나온다.
- 희귀도와 실시간 가격(확정): 모든 아이템 정의에 희귀도와 실시간 가격을 둔다. 바닐라 아이템 정의도 포함한다. 세부 설계는 [minecraft_integration_plan.md](minecraft_integration_plan.md)의 "희귀도와 실시간 가격"에 둔다.

## 부동산

| 기능 | 설계 |
|---|---|
| 매물 | 국가·지역별 필지/건물. 용도는 주거·상업·토지. 공급은 개발 법인이 하고 관리자가 승인한다. |
| 매매 | 취득세 + 중개수수료(플랫폼) + 매도자 양도세. 호가 거래. |
| 임대 | 월세는 정기 자동 납부, 전세는 보증금 에스크로. 연체 → 계약 해지 → 알림. |
| 보유세 | 재산세를 주기적으로 국고에 납부. 미납은 신용점수에 반영. |
| 대출 연동 | 부동산 담보대출을 `bank_manager`에 LTV/DTI 규칙으로 연결. 담보 매각은 기존 회수 절차 재사용. |
| 가격 | 지역 지수가 금리, 공급, 사건에 반응. |
| 금융 연결 | 펀드의 `real_estate` 구성자산 연결. REIT와 배당은 이후 단계. |
| 거주 | 거주지는 마인크래프트 서버 안에서 설정하게 할 예정이다(확정). 거주지 기반 세율은 그 기능이 생긴 뒤 연결한다. 그 전에는 기존 국적 기준 규칙을 쓴다. |

## 온라인 쇼핑몰

- 입점: 법인이 판매자로 입점해 상품을 등록한다. 플랫폼 법인이 수수료를 받는다.
- 주문: 재고 차감, 배송 지연 타이머, 환불과 분쟁 절차. 판매자 평점으로 노출 순서를 정한다.
- 해외 직구: 상품 통화가 구매자 통화와 다르면 정산 규칙대로 해당 통화 계좌로 결제하고, 없으면 실시간 환전으로 결제한다.
- 상품: 소모품(반복 구매), 내구재(보유 자산, 감가상각), 한정판(수집·재판매).
- UI: HTS 안에 탭으로 넣고 공식 사이트(NACURI)는 소개/랜딩만 맡긴다. 구현 우선순위는 HTS가 먼저, 디스코드 명령어는 이후다(확정). 관리자 대시보드 도구는 보류.

## 일일 출석 보상

돈이 생기는 곳(faucet)이므로 총량 상한이 필수다.

- 구조(확정): 기본소득 구조를 재사용한다(`admin_manager.distribute_basic_income`, `basic_income_payments`: 국고 재원, 국가 통화, 지급 기록, 환율 기록). 추가 기능은 추후 구현한다.

- 보상 종류: 소액 화폐, 뽑기권, 강화 재료. 화폐는 최소로 하고 아이템 중심을 권장한다.
- 재원: 국고. 국가별 일일 지급 상한을 두고 소진 시 중단한다.
- 연속 출석: 7일, 14일, 30일 마일스톤 보너스. 하루 놓치면 리셋 대신 유예 1일(구제권).
- 기준 시각: 하루 경계 시각을 하나 정한다(`time_utils` 재사용).
- 어뷰징 방지: 가입 후 N일 경과와 최소 활동 조건. 청구는 멱등으로 처리해 중복 수령을 막는다.
- 알림: 출석 가능 알림과 마일스톤 도달 알림을 벨로 보낸다.

## 랜덤뽑기

복권(`lottery_manager`)은 상금(돈), 뽑기는 아이템으로 분리한다. 난수와 시드·결과 기록은 복권의 방식(`secret + entropy`로 SHA-256 카운터, `secrets` 기반)을 재사용한다(확정). 추가 기능은 추후 구현한다.

| 항목 | 설계 |
|---|---|
| 결제 | 통화 계좌 정산 규칙. 비용은 운영 법인과 국고로 이전. |
| 풀 | 뽑기 상자(배너)마다 등급별 확률표와 기간. 관리자가 등록. |
| 확률 | 화면에 공개. 시드와 결과를 저장해 사후 검증 가능하게 한다. 서버 측 난수. |
| 천장 | N회 연속 미당첨이면 상위 등급 보장. 카운터는 배너별 보존. |
| 1회 / 10연 | 10연은 하위 등급 1개 보장 정도의 보정만. |
| 중복 | 중복 아이템은 강화 재료로 전환. |
| 한도 | 일일/월간 구매 한도. 계정 설정으로 낮출 수 있다. |
| 환급 | 미사용 상자 환불 정책 필요. 사용 후 불가. |

## 아이템 강화

| 항목 | 설계 |
|---|---|
| 단계 | +0 ~ +N. 단계가 오를수록 성공 확률 하락. |
| 비용 | 재료 + 화폐. 단계마다 증가. 화폐는 국고와 운영 법인으로 이전. |
| 실패 | 유지, 하락, 파괴 중 단계별로 다르게. 파괴는 높은 단계에만 적용 권장. |
| 보호 | 보호 주문서(소모품)로 파괴 방지. 쇼핑몰 판매 상품이 된다. |
| 천장 | 연속 실패 시 다음 성공 확률을 올리는 누적 보정. |
| 효과 | 용처는 나중에 정한다(보류). 정하기 전까지 능력치는 표시값이다. |

## 매출–주가 상호작용 (신규 기획)

소비로 생긴 법인 매출·이익이 주가에 반영되게 하되, 조작과 과열을 막는다. 주가는 지금 시장 엔진과 사건으로 움직이므로, 실적은 그 입력 중 하나로 더한다. 구현 때 `auto_target_engine`과 `market_events`가 받는 입력 형태를 먼저 확인한다.

### 흐름

1. **입력(실적):** 법인 원장의 기간별 매출, 영업이익, 이익률, 매출 성장률(`CompanyAccounts.financial_report`, `company_income_log`과 소비 엔진의 판매 분개). 기간은 경제 시간 기준 분기로 한다.
2. **기대치:** 직전 기간 실적과 법인 자체 이동평균(또는 업종 평균)으로 기대 이익을 만든다.
3. **서프라이즈:** (실적 − 기대치) ÷ 기준값. 임계값 이하는 무시한다.
4. **가격 반영:** 서프라이즈를 시장 사건 또는 자동 목표가 보정으로 바꾼다. 한 번에 반영하는 최대 변동폭에 상한을 두고, 여러 구간에 나눠 반영한다. 주가가 PSR/PER 허용 범위를 벗어나면 증폭하지 않고 감쇠해 과열을 막는다.
5. **배당 연결:** 이익은 배당 재원이 될 수 있다(기존 `corporate_actions`). 배당 정책과 이익 규모를 연결한다.
6. **공시:** 실적 발표를 벨 알림과 HTS 공시로 알리고, 발표 시점에 가격에 반영한다. 발표 전 거래 제한은 후속 과제다.

### 조작 방지

- **자기거래 제외:** 같은 소유자나 특수관계 계정이 자기 법인에서 산 매출은 실적에서 제외하거나 가중치를 0으로 한다. 기존 지배구조 그래프(`_trace_effective_owners`)를 활용한다.
- **집중도 한도:** 상위 구매자의 매출 비중이 상한을 넘으면 초과분은 실적으로 인정하지 않는다.
- **환불 반영:** 환불과 정정은 실적에서 차감한다. 기간 마감 후 환불은 다음 기간에 조정한다.
- **세탁형 반복 구매:** 소액 반복 구매는 `compliance_manager`/AML 경보와 연결한다.
- **설정값:** 변동폭 상한, 감쇠, 기간 길이는 코드 상수가 아니라 관리자 설정값으로 둔다.

### 검증

시뮬레이션으로 변동폭 상한이 폭주를 막는지 확인하고, 자기거래 공격 시나리오를 테스트한다.

## 중고거래 (사용자 간 거래) (신규 기획)

사용자끼리 아이템을 사고파는 시스템이다. 법인 상점(쇼핑몰)과 달리 판매자가 개인이다.

| 항목 | 설계 |
|---|---|
| 대상 | 아이템 개체(고유 ID 단위). 소모품은 수량 단위 묶음. 부동산은 별도 매매 경로를 쓴다. |
| 방식 | 고정가 등록(기본), 가격 제안(오퍼), 경매(후속). 기존 주식 주문장은 쓰지 않고 별도 리스팅 테이블을 둔다. |
| 에스크로 | 등록하면 아이템을 잠그고, 구매 시 대금과 아이템을 한 트랜잭션으로 교환한다. 등록 취소·만료 시 아이템을 돌려준다. |
| 상태 고정 | 등록 시점의 강화 단계, 내구도를 스냅샷으로 고정해 거래 직전에 바꾸는 사기를 막는다. |
| 결제 | 정산 규칙을 따른다. 구매자는 상품 통화 계좌가 필요하고, 개인 판매자가 해당 통화 계좌가 없으면 `PayoutManager`의 선택(환전/임시계좌)을 쓴다. |
| 수수료·세금 | 플랫폼 수수료와 거래세/양도차익세를 세금 서비스를 통해 부과한다. 세율은 설정값이다. |
| 시세 | 아이템 정의별 최근 체결가, 최저 등록가, 평균가를 보여 준다. |
| 신뢰 | 판매자 평점, 신고, 거래 이력. 비정상 저가·고가 반복 거래는 `compliance_manager`/AML 경보로 보낸다. |
| 한도 | 계정당 동시 등록 수, 등록 수수료(스팸 방지). |
| 알림 | 판매 완료, 오퍼 도착, 만료를 벨로 보낸다. |

원장은 쇼핑몰과 같은 분개 경로를 쓰고, 아이템 소유권 이전은 아이템 시스템의 `owner`/`version` 규칙을 거친다.

## 세금 시스템 (별도 기획 예정)

현실적인 세금 시스템을 구축할 예정이다(확정). 이 문서의 모든 세금은 세금 서비스 한 곳을 호출하도록 만들고, 세율과 규칙은 설정값으로 둔다. 세금 시스템이 완성되기 전에는 임시 단일 세율로 시작한다.

| 세금 | 적용 |
|---|---|
| 부가가치세/소비세 | 쇼핑몰·서비스 구매 |
| 취득세 | 부동산·고가 아이템 취득 |
| 재산세 | 부동산 보유 |
| 양도소득세/거래세 | 부동산 매매, 중고거래 차익 |
| 법인세 | 법인 이익 |
| 소득세 | 개인 판매자 소득 |

기존 세금 구조(`functions/tax_calc.py`, `database/tax_db.py`, 소득별·국적별 규칙)와의 통합 방식은 세금 시스템 기획에서 정한다. 거주지 기반 세율은 거주지 설정 기능이 생긴 뒤 연결한다.

## 정기 작업과 시간 기준

- **대상:** 월세·전세 만기, 재산세, 출석의 날 경계, 배송 타이머, 뽑기 배너 기간, 상품 만료.
- **확정:** 정기 작업은 만들되 백엔드 로직은 보류한다.
- **확정:** 앞으로 INAZINA 시스템 시간 단위는 마인크래프트 서버 내 시간이다. 비율과 방식은 마인크래프트 문서의 "경제 시간"에서 정한다.
- **백엔드 착수 때 지킬 원칙:** 시간 조회는 한 모듈에서만 한다. 작업은 기간 키로 멱등하게 만든다. 대량 처리는 청크로 나눠 전역 쓰기 락(`_run_background_write`)을 오래 잡지 않는다. 재시작해도 안전해야 한다.
- **주의:** 현재 코드는 `time.time()`을 직접 쓰는 곳이 많다(예: `PayoutManager`의 30일 보관). 시간 기준 전환은 별도 작업이며 진행 중인 대출·예금 만기의 전환 규칙이 필요하다.

## 마인크래프트 연동과의 경계

마인크래프트 연동은 별도 계획이며, 이 문서의 구현이 연동 때문에 복잡해지지 않도록 아래만 지킨다.

- **서비스 계층 분리:** 소비·뽑기·출석·강화의 도메인 로직은 `managers/`에 두고, 디스코드·HTS·API는 얇은 입구로 둔다. 나중에 다른 입구(플러그인)가 같은 로직을 부를 수 있어야 한다.
- **아이템 개체 식별:** 아이템 개체는 고유 ID(UUID)와 소유자, 위치(`location`), 버전(`version`)을 처음부터 가진다. 웹에서는 `location`이 항상 웹 보관이다.
- **확장 필드 예약:** 아이템 정의에 연동용 확장 데이터(JSON 한 칸)를 둘 수 있게 하되, 이 문서의 기능은 그 값을 쓰지 않는다.
- **능력치는 데이터로:** 강화 단계별 능력치와 확률, 비용은 코드가 아니라 정의 데이터로 둔다.
- **PostgreSQL 호환:** 새 테이블은 SQLite와 PostgreSQL 양쪽 스키마로 만든다.
- **시간 단위(확정):** 앞으로 INAZINA 시스템 시간 단위는 마인크래프트 서버 내 시간을 따른다. 날·월 기준은 한 모듈에서만 조회한다. 정의와 설계는 [minecraft_integration_plan.md](minecraft_integration_plan.md)의 "경제 시간"에 둔다.

위 약속 외에 마인크래프트를 위한 기능은 이 문서의 범위에 넣지 않는다.

## 그 외 소비처 후보

우선순위 순: 공공요금·구독, 외식·여가·여행, 자동차·내구재, 보험(예금보험 구조 재사용), 교육·자격증, 벌금·수수료·공공서비스.

## 경제 균형

- 출석과 판매로 들어오는 양 ≤ 뽑기, 강화, 소비로 나가는 양이 되도록 국가별 지표를 본다.
- 관리자 대시보드에 일일 발행/소멸 총량, 아이템 총 보유량, 확률 실측치를 표시한다.
- 조절 수단: 출석 상한, 뽑기 가격, 강화 비용, 아이템 풀 교체.

## 위험 요소

- 원장: 모든 거래가 공통 전기에 연결돼야 한다. M4와 함께 가야 하므로 1단계가 가장 오래 걸린다.
- DB: SQLite와 PostgreSQL 이중 지원.
- 밸런스: 소득 대비 가격이 틀어지면 파산(insolvency)이 늘어난다. 소비로 인한 파산은 허용하며 구매 한도는 두지 않는다(확정). 5단계 시뮬레이션 필요.
- 시간 기준 전환: 시스템 시간 단위를 마인크래프트 서버 내 시간으로 바꾸는 것은 이자, 만기, 거래 시간 등 기존 시스템 전반에 영향을 준다. 현재 코드가 `time.time()`을 직접 쓰는 곳이 많다.
- 확률형 요소: 한도, 확률 공개, 서버 측 난수와 시드 기록은 필수.
- 작업 트리: 다른 세션의 미커밋 변경이 많으므로 구현 때는 경로를 지정해 스테이지한다.

## 결정 사항

### 확정 (2026-11-18)

- 판매자는 현존하는 법인을 구조 변경 없이 그대로 쓴다. 법인은 모든 화폐의 계좌를 가진다.
- 매출–주가 상호작용을 기획에 추가한다(위 섹션).
- 출석 보상은 기본소득 구조를 쓰고 추가 기능은 추후 구현한다.
- 뽑기 난수는 복권 방식을 재사용하고 추가 기능은 추후 구현한다.
- 착수 시점은 Milestone 프로젝트(M4, M6–M8) 완료 후다.
- 정기 작업은 만들되 백엔드 로직은 보류한다. 시스템 시간 단위는 앞으로 마인크래프트 서버 내 시간이다.
- 현실적인 세금 시스템을 구축할 예정이다(별도 기획).
- 소비로 인한 파산을 허용하고 구매 한도는 두지 않는다.
- 거주지는 서버 안에서 설정하게 한다.
- 테스트를 시행한다. HTS를 우선한다.
- 중고거래(사용자 간 거래)를 추가한다.

### 보류 (나중에 정한다)

- 강화 효과의 용처(정해지면 강화 비용·확률 곡선을 설계한다)
- 부동산 가격 모델(지역 지수 자동 / 관리자 사건)
- 강화 실패 시 아이템 파괴 여부
- 뽑기 결제 수단(일반 통화 계좌 / 전용 포인트)
- 관리자 대시보드 도구

### 구현 전에 확인할 것

- 법인이 모든 화폐 계좌를 가질 수 있는지: 현재 `issuer_cash_accounts`의 단일 balance와 `company_cash_to_issuer` 트리거 구조가 다통화 법인 계좌를 지원하는지 조사한다.
- `time.time()`을 직접 쓰는 지점 목록(시간 기준 전환 범위).
- 매출–주가: `auto_target_engine`과 `market_events`의 입력 형태.
- 1단계(소비 엔진 코어)의 원장 작업 규모: 소비 유형마다 `post_*`와 `reconcile_*` 쌍이 필요하다. 1a 결제·세금 단일 경로, 1b 환불·정정, 1c 대사 게이트로 쪼갠다.
