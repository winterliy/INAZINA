# 큰 금액(10^18 이상) 정확 처리

100경(10^18)을 넘는 금액을 한 단위도 잃지 않고 저장·계산·전송·표시하는 방법을 정리한다. 운영 DB는 이 형식으로 이미 전환됐다.

## 현재 상태 (구현 완료)

- **저장 형식**: 금액 열은 TEXT다. 작은 값은 평범한 정수·실수로, 안전 범위(2^53-1)를 넘는 값은 태그를 붙인 정확한 10진 문자열로 저장한다. `~M~…`은 정확한 금액, `~R~…`은 REAL 선언 열의 값이다. 코덱은 `database/wide_values.py`.
- **연산**: `UnifiedConnection`(`database/unified.py`)이 모든 SQL을 `database/wide_sql.py`(SQLGlot)로 변환해 `WIDE_ADD`·`WIDE_SUB`·`WIDE_CMP` 같은 정확한 SQLite 함수를 호출한다. 합계(`SUM`·`AVG`)와 정렬 collation(`wide_numeric`)도 정확한 구현이다. 어떤 열이 금액인지는 `database/money_columns.py`의 등록부가 정한다.
- **한계값** (`functions/amount_limits.py`): 네이티브 금액 `MAX_NATIVE`=10^24, 최소단위 `MAX_MINOR`=10^30, 이자 하위단위 `MAX_SUBMINOR`=10^36, Decimal 정밀도 100자리. 금액 열에는 `CHECK(WIDE_VALID_MONEY(...))`가 걸려 있다.
- **파이썬 값**: 큰 값은 `ExactDecimal`(`functions/exact_money.py`)로 다루고, JSON으로 내보낼 때는 문자열로 보낸다.
- **웹**: `apps/shared/money.ts`가 문자열·BigInt로 파싱·표시·덧셈을 한다. `Number`는 차트 좌표 같은 근사치에만 쓴다.
- **전환 도구**: `database/wide_migration.py`의 `migrate_copy(원본, 새경로)`가 읽기 전용 원본을 새 DB로 복사한다. 원본 DB에는 `wide_money_schema` 테이블(버전 1)이 생겨 이관 여부를 표시한다.
- **검증 테스트**: `tests/test_wide_*.py`, `tests/test_decimal_binding.py`, `tests/test_numeric_guards.py`.

### 운영 주의

- **이 형식을 읽는 현재 코드로만 DB를 열어야 한다.** 예전 코드로 열면 금액을 읽지 못한다. 이전 형식으로 되돌릴 때는 전환 전 백업(`database/backups/inazina-20261101-003145-before-wide*.db`)을 쓰는데, 그 뒤의 거래는 사라진다.
- **DB 전환 절차**: 서비스 중지 → WAL 체크포인트 → 백업 → `migrate_copy`로 사본 생성 → 원본과 사본의 모든 행·값 비교 → `DatabaseManager`를 사본에서 두 번 시작해 검사 → 원본을 원자적으로 교체 → 서비스 재시작 → 큰 금액 송금 왕복 확인.
- 전환과 검증은 운영 DB에서 직접 하지 말고 사본에서 먼저 한다.

### 겪은 함정

- 작은 값에 큰 값을 더해 안전 범위를 넘기는 경계는 정확히 처리되지만, 이를 깨는 실수는 대부분 float이 끼는 곳이다(JSON Number, `float()` 변환, `round`).
- SQL 변환기는 SQLite의 모든 문법을 지원하지 않는다. 예를 들어 `UPDATE OR IGNORE`는 변환되지 않으니 표준 SQL로 쓴다.
- `credit_events`는 수정·삭제가 막힌 감사 기록이다. 정리 작업에서 건드리지 않는다.
- pytest-xdist는 `subTest` 인자의 큰 정수(10^24)를 전달하지 못한다. 인자는 문자열로 넘긴다.
- 서버가 비율을 문자열로 보내는 곳이 있다. 화면에서 `.toFixed`를 부를 때는 `Number()`로 감싼다.

## 설계 근거
### 사용자 요구
- 사용자·법인·국가 및 모든 금융상품의 금액 처리 범위를 적어도 100경으로 확장한다.
- 100경 = 1,000,000,000,000,000,000 = 10^18 통화 단위다.
- 잔액, 송금, 주문가격·대금·예치, 환전, 대출, 이자, 세금, 배당, 펀드, 파생상품, 회계와 합계가 대상이다.
- 큰 값은 화면에서 경·조 또는 과학적 표기법으로 표시할 수 있으나 저장·계산에서 하위 단위를 잃어서는 안 된다.


### 접근 비교와 권장안
1. 한도 상향 및 REAL/과학적 표기 저장: 빠르지만 100경 ± 1을 구별할 수 없다. 채택하지 않는다.
2. 모든 금액을 정수 문자열로 저장하고 Python int/Decimal로 계산: 기존 SQLite 운영환경을 유지하면서 정확성을 보존한다. 권장한다.
3. PostgreSQL NUMERIC으로 DB 교체: 정확한 SQL 계산을 제공하지만 배포·백업·운영 환경과 전체 DB 계층을 바꿔야 한다. 현재 요청보다 운영 변경이 크다.

선택한 안은 2번이다. 아래가 그 설계다.

### 금액 계약
- 금액은 통화 코드·소수 자릿수와 함께 다룬다. authoritative 값은 최소단위 정수이며 DB/JSON에서는 정규화된 10진 정수 문자열이다.
- Python 계산은 int/Decimal로 수행하고, 이자 잔여는 기존 subminor scale을 유지한다. Decimal context는 최대 지원금액과 중간 곱셈에 충분하도록 명시한다.
- 지원 범위: 각 네이티브 금액의 절댓값 10^24까지, 소수 자릿수 0~6 및 subminor 6자리. 최소단위/중간 합계에는 네이티브 한도를 잘못 적용하지 않는다. 이는 100경보다 여유 있는 범위다.
- 입력은 10진수와 1e18 형태를 허용한다. NaN, Infinity, 과도한 지수 및 통화 최소단위 이하 금액은 명확히 거부한다.
- 수량·신용점수·비율·시각·ID는 금액이 아니며 기존 별도 규칙을 유지한다.
- 기존 FLOAT 데이터에서 이미 소실된 자릿수는 복원했다고 주장하지 않는다. canonical 정수와 mirror가 충돌하면 자동 이관을 중단하고 차이를 기록한다.

### DB와 SQL
- [finance.md의 금액 필드 인벤토리](finance.md#통화-금액-필드-인벤토리-m4-종료-기준) 및 런타임 registry로 금액 열·트리거·인덱스·제약을 열거한다. legacy REAL mirror는 계산의 원본으로 쓰지 않는다.
- 모든 writable/read-only/웹 연결에서 exact 정수/decimal SQL 함수를 등록한다. 문자열 금액의 SUM, +, -, *, /, 비교, ORDER BY를 SQL native 연산에 맡기지 않는다.
- 금액 변경은 기존 트랜잭션 안에서 canonical 정수를 읽고 Python으로 계산해 조건부 갱신하거나, 명시적 exact SQL 함수로 원자적으로 처리한다. 문자열 사전순 비교는 금지한다.
- 통화·금액 범위·대사·이중지출 방지 제약을 exact 값 기준으로 재작성한다. 이관하지 않은 경로에서 wide 금액을 쓰는 것은 fail closed한다.
- 실DB 전체 백업 → 복제본 이관 → row count/통화별 합계/원장·지갑 대사/FK 검사 → 쓰기 중단 → 원본 이관. 이관은 재실행 가능하고 실패 시 롤백한다.
- 유동성 총공급량 등 집계도 SQLite int64 SUM을 피하고 exact 집계한다.

### 금융 도메인
- 지갑·국고·법인·계좌의 정수 canonical API를 공통 사용한다. 모든 금융거래의 차감·입금·세금·원장 항목은 같은 canonical 금액을 사용한다.
- 가격 엔진은 float로 만든 변동률을 Decimal 가격에 적용하고 통화별 최소단위에서 한 번 반올림한다. native double 구현은 안전범위 밖에서 정확한 Python 경로로 전환한다.
- 개인, 법인, 국가, 은행, 펀드 간 모든 거래를 통화별로 보존하고, 실패 시 원장·잔액·예치금을 모두 롤백한다.

### API와 UI
- 금액 필드는 명시적 decimal/integer 문자열 DTO로 전달한다. JSON 직렬화에서 큰 int를 Number로 보내지 않는다.
- TypeScript는 금액 문자열과 bigint 최소단위를 사용한다. Number()는 차트 비율·좌표 등 근사치가 필요한 경계에만 사용한다.
- 대시보드·나루·공유 인증/명령/폼·Discord 입력에 동일 금액 parser/formatter를 적용한다.
- 경·조 및 과학적 표시 옆에 전체 정확한 값과 통화를 확인할 수 있게 한다. 입력·확인창·저장·재조회가 같은 값을 보존한다.

### 완료 기준
- 100경, 100경±최소단위, 100경 간 송금, 100경 이상의 합계, 0/음수/초과한도, 0/2/6자리 통화 테스트.
- 사용자·법인·국가·은행·펀드 및 주문/대출/세금/이자/배당/파생상품의 end-to-end 보존·원장 대사·롤백 테스트.
- API JSON 왕복, 1e18 입력, UI 표시/확인/수정, 재시작, 기존DB 이관 및 재실행 검증.
- 기존 테스트, 타입체크, 빌드와 native fallback 비교를 모두 통과해야 전체 지원이라고 보고한다.

### 구현자가 확정할 기술 규칙
- 전체 금액 registry를 table/column/currency/scale/canonical-source로 고정하고 미등록 금액 경로를 정적 검사로 찾는다.
- Python Decimal localcontext precision=100, 최종 최소단위 ROUND_HALF_UP. 분할 지급은 정수 나눗셈과 최대잔여 배분으로 합계를 보존한다.
- DB 금액 갱신은 exact SQL UDF를 사용한 단일 조건부 UPDATE를 표준으로 삼고, 모든 연결에서 동일 UDF를 등록한다. SQL native SUM·산술·비교가 남아 있는 금액 경로는 이관 완료로 보지 않는다.
- JSON DTO는 {units: 정수문자열, currency: 코드, decimalPlaces: 정수}로 통일한다. API schema version을 올리고 구버전 클라이언트와 봇 연결의 쓰기를 거절한다.
- 가격 엔진의 금액 입력/latent/result는 Decimal 또는 정수 최소단위로 유지한다. float는 확률·변동률에만 허용한다.
- 이관 전 봇·웹의 쓰기를 중단하고 모든 기존 연결을 닫는다. 재시작 시 schema version 검사를 통과한 프로세스만 쓰기를 허용한다.
- 주식분할 시 주당 원가가 최소단위 미만으로 내려가도 취득원가 총액을 잃지 않도록 lot별 총원가를 보존하고 부분 매도에 배분한다.

## 불변 조건

- 최대 한도는 위 값이다. 통화 소수 자릿수는 0~6이고, 수량·신용점수·시각 한도는 금액과 별도다.
- 지원하지 않는 SQL, NaN·Infinity, 과도한 지수, 잘못된 단위는 거부한다(fail closed).
- 모든 금액 갱신은 트랜잭션 롤백과 합계 보존을 유지한다. 옛 데이터에서 이미 사라진 float 정밀도를 되살렸다고 주장하지 않는다.
- 10^18±최소단위가 연산·합계·비교·JSON 왕복 뒤에도 구별되어야 한다.
- 트리거 산술, 조건부 차감, 정렬은 문자열 비교나 SQLite REAL이 아니라 10진 의미를 따른다.
- 사용자 ID·계좌번호·수량은 금액이 아니므로 그 의미를 바꾸지 않는다.
- 안전 범위를 넘는 가격 경로는 float 구현을 쓰지 않고 정확한 경로로 전환한다.
