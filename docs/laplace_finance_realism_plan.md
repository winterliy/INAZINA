# LAPLACE 금융 시뮬레이터 현실화 계획

목표는 실제 금융기관 운영 시스템이 아니라 현실 요소를 갖춘 금융 시뮬레이터다. 기존 기능과 데이터 구조를 최대한 재사용하며, 겹치는 기능은 재작성하지 않고 확장한다. 기준금리 결정권은 관리자에게 둔다.

## 보안·준법 작업 흐름

웹 로그인은 Discord OAuth, 서명 세션 쿠키, 비밀번호 해시 및 로그인 제한 기반이 있다. `admin_audit`에는 관리자 작업이 append-only로 기록되고 KYC/AML 검토에도 별도 불변 이벤트 이력이 있다. KYC는 실명·신분증·증빙 원본 없이 상태·위험등급·고정 사유 코드만 보존한다. KYC 프로필이 명시적으로 존재하는 고객은 유효한 `verified` 상태이고 `restricted` 등급이 아닐 때 개인 송금, 예금계좌 개설, 대출 신청을 할 수 있으며 송금 수취는 허용한다. KYC 차단 결정은 요청 작업 코드·고객의 당시 상태/위험등급·고정 사유 코드로 append-only 이벤트에 남겨 관리자 타임라인에서 조회한다. 기존 KYC 프로필이 없는 계정은 기존 시뮬레이터 동작을 유지한다. HTS는 본인의 KYC 상태·위험등급·만료일을 보여준다. AML은 송금인과 수취인을 각각 감시하고, 양쪽 국가 통화로 거래액·최근 24시간 누적액·횟수를 환산해 경보한다. 누적액 경보는 당시 총 누적액을 이력에 기록한다. 과거 외화 거래는 거래 시점 고시 환율이 저장되지 않아 경보 평가 시점 환율로 환산한다. 임계치는 기본 비활성이고 운영자가 시뮬레이터 정책으로 설정하며, 법정 기준이나 법적 신고 판정이 아니다. 인증 관리자 전용 `/internal/admin/compliance` API와 대시보드에서 KYC 검토, AML 규칙 설정·사례 검토와 최근 이벤트 조회가 가능하다. 보존/열람 정책·심사 준비용 통제 증빙은 남아 있다. 실사용 신분증 원본은 목적·관할·보존기간·접근통제를 정하기 전에는 수집하지 않는다.

## 순서와 최소 변경 원칙

1. 기존 테이블·서비스를 재사용해 기대신용손실을 연결한다.
2. 기존 기관 손익원장을 유지하며 불변·균형 검증을 갖춘 상품화폐 최소단위 은행 분개장을 병행 구축하고, 거래 유형별로 점진 연결한다.
3. 조달원, 자본, 유동성, ALM 규제를 기존 `financial_institutions`와 기관 원장에 확장한다.
4. 거시·시장 입력과 금리곡선의 전달·대체 규칙을 추가한다.
5. 기존 차주·담보·계약 흐름에 리스크 등급, 법률·세금 규칙, 채무조정을 연결한다.
6. 예금보험·은행정리 및 외화위험을 기관 건전성 모델에 통합한다.
7. 채권 위험지표와 금리 파생·헤지를 기존 시장 인프라 위에 추가한다.
8. 보안 검토 후 KYC·AML·공통 감사로그 및 규제 심사 증빙을 연결한다.
9. 금리·예금인출·대량부도·환율 스트레스, 회계 불변식과 국가별 규칙 검증을 완료선으로 둔다.

주식예탁증서(DR)는 [GitHub issue #80](https://github.com/winterlies/INAZINA/issues/80)의 별도 자산 유형으로 기존 주문·자산 시스템에 연결한다. 게임 내 정수 원주 예탁/DR 발행과 풀링 원주 상환 원장은 구현하지만 실제 예탁기관·수탁사 보관 증명은 제공하지 않는다.

## 전체 완료까지의 작업분해(WBS)

아래 순서는 현재 구현을 기준으로 한 완료 체크리스트다. “완료”는 해당 시뮬레이터 내부 기능과 테스트가 있다는 뜻이며, 실제 은행·수탁기관의 운영 적합성이나 규제 인증을 의미하지 않는다. 12개 챕터와 #80은 완료조건이 다르므로 서로 독립적으로 추적한다.

### M0 — 기준선·범위 잠금

- [x] 기존 서비스·DB·웹 API·원장과 유사 기능을 확인하고 중복 재작성을 피한다.
- [x] 내부 시뮬레이션 전용으로 한정하고, 실제 금융·수탁·신원확인기관 연결은 제외한다.
- [x] 기준금리 결정권은 관리자에게 둔다.
- [x] 현재 계획/작업트리 기준 테스트 기준선과 변경 소유 범위를 기록한다. 단, 작업 시작 전부터 dirty 상태여서 clean HEAD 대비 사전 기준선은 복원·추정하지 않는다.

### M1 — #80 DR 의결권

- [x] 기준 시점 보유량으로 직접 원주·DR 전환비율·위임분을 동결한다.
- [x] 관리자 API에서 기준 스냅샷과 안건을 만들고, 기준일 자격자가 안건별 한 번 투표한다.
- [x] 의결권 수에 따른 가중 집계·관리자 결과 조회·감사 이벤트를 제공한다.
- [x] 관리자 확정 투표 시작/마감 epoch, 마감 전후 투표 거부와 0~100% 정족수 기준을 추가한다.
- [x] 마감 후 투표율과 정족수 충족 여부를 조회 결과에 포함한다.
- [x] HTS에서 사용자 본인 안건·기준일 권리·투표기간·투표를 확인하고 투표한다.
- [x] 관리자가 대시보드에서 회의·안건·투표기간·정족수를 관리하고 결과를 본다.
- [x] 회의·투표 불변식, 중복 투표, 위임·보유변경 경계 테스트를 추가한다.

### M2 — #80 내부 수탁·결제·수수료

- [x] 기존 동기 전환에 요청 단위 상태 집계(`requested → verified → settled`)와 별도 append-only 상태 이벤트를 추가하고, 기존 단계 이벤트를 새 원장으로 이관한다.
- [x] DR 프로그램별 내부 결제 지연(0~30일)을 설정하고, 지연이 양수인 발행/상환 요청은 대기 상태로 접수한다. 기본값 0은 기존 즉시 전환 동작을 보존한다.
- [x] 지연 요청의 입력 원주 또는 DR 수량을 예약하고, 매도 주문·직접 매도·대출담보·커버드콜 담보·다른 DR 요청에서 이중 사용을 막는다.
- [x] 사용자가 Discord `/dr전환`과 HTS에서 요청하며, HTS에서 상태/정산 가능 시각을 조회·취소하고, 관리자는 대시보드 대기열을 조회·취소·거절하거나 정산 가능 시각 이후 처리한다.
- [x] 취소/정산 완료 시 예약을 해제하고, 정산 실패는 원자 롤백으로 대기 요청과 예약을 보존한다. 참조 키 기반 재호출은 중복 정산을 방지한다.
- [x] 기존 예약 정산 루프에 만기 DR 전환 자동 처리(최대 100건/회)를 연결한다. 정산 오류는 요청/예약을 유지하고 워커 로그에 요약해 재시도할 수 있다.
- [x] 정산 가능 시각이 24시간 지난 미처리 요청을 관리자 웹에서 경고하고, 요청별 자동 정산 시도 횟수와 최근 오류를 노출한다.
- [x] 요청·검증·대기·정산·거절·취소 상태와 유효한 전이만 허용하는 append-only 이벤트를 정의한다. 거절은 제한된 사유 코드와 함께 기록한다.
- [x] 정산 시도별 성공/실패·시각·실패 사유를 별도 append-only 기록으로 보존하고 관리자 목록에 시도 횟수와 최근 사유를 노출한다.

금액 필드 인벤토리 문서([`financial_amount_inventory.md`](financial_amount_inventory.md))와 `financial_amount_snapshots` 등록부를 추가했다. 등록된 범위는 원본 변경 시 통화별 정수 최소단위 미러로 갱신되고 `audit_amount_snapshots`가 누락/불일치를 보고한다. 이 레지스트리는 업무 테이블을 정수값으로 대체하지 않으므로 M4 이관 완료 증거가 아니다. 계좌 quantum guard가 드러낸 기존 경로 두 곳도 수정했다: 외화 레거시 이자는 spendable 잔액에 최소단위만 지급하고 잔여 Decimal을 이월하며, 구형 계좌 삽입은 통화 최소단위로 먼저 정규화한다. M4 여섯 완료항목은 아직 모두 미체크다.

상각 후 계약상 메모잔액(`loans.charged_off_balance`)도 계약통화 정밀도 guard와 정수 최소단위 snapshot 등록부에 연결됐다. 이는 M4 원천→최소단위 미러의 추가 범위일 뿐, 대출/상환·시장·상품·채권의 권위 저장값 이관으로 간주하지 않는다.

대출 계약 현금흐름 산출과 회차 지급 배분(`_loan_cashflows`, `_allocate_schedule_payment`, `_apply_schedule_installment`)은 이제 원금 분배·잔액 이월·수수료→이자→원금 배분 중간값을 계약통화 최소단위 정수로 처리하고, 저장/기존 호출 경계에서만 legacy 금액값으로 변환한다. USD 센트 단위 통합 테스트가 현금흐름 원금 총액, 분할배분과 금액 snapshot을 확인한다. 상환 스케줄 DB 열과 다수의 이자/상환 호출부는 아직 legacy 수치 필드를 사용하므로 전체 대출 금액 경로의 canonical-unit 이관은 미완료다.

`BankJournal.reconcile_loan_payment_schedules`는 대출 상환표를 계약통화 최소단위로 환산해 회차별 `amount_paid == fee_paid + interest_paid + principal_paid`, 각 지급 구성요소가 해당 예정액을 넘지 않는지, `paid` 상태가 총 예정액과 일치하는지 검사한다. 이 검사는 기관 통합 대사에 포함되고 관리자 은행원장 API/대시보드에도 불일치 회차를 노출한다. USD 센트 기준 정상/불일치 탐지 테스트가 추가됐다. 이는 상환표 내부 불변식 검사이지 은행 현금·고객 지갑·대출 원장의 전사 현금흐름 대사는 아니다. M4 완료 체크 항목은 아직 모두 미체크다.

대출 상환표의 예정 원금·이자·수수료와 지급 총액·구성요소 각각에 계약통화 최소단위 정수 열을 추가했다. 기존 행은 legacy 수치에서 통화 scale로 백필되고, insert/update 호환 트리거가 구형 writer 경로도 정수 열과 동기화한다. 대출 지급 배분과 상환표 내부 대사는 이제 정수 열을 우선 읽으며 legacy 금액 열은 호환 인터페이스로 보존한다. USD 1.10/1.20/1.95 배분의 정수 열과 구형 열 일치를 회귀 검사한다. 아직 loan balance·이자 발생·상환 원장/시장·상품·채권 등 다른 금액 경로까지 이관된 것은 아니므로 M4 미완료다.

상환표 대사는 정수 열과 legacy 호환 금액의 통화 scale 변환값이 서로 다르면 해당 회차와 필드를 별도 불일치로 노출한다. ECL의 midpoint EAD proxy도 미래 원금 상환 차감에 이 정수 열을 사용하므로 회계 이관 금액과 신용위험 경로가 같은 원천을 읽는다. USD 일정에서 legacy/정수 값이 일부러 달라진 경우 EAD가 소액단위 값을 따르고 대사가 drift를 잡는 회귀 테스트가 추가됐다.

## 첫 적용: 기대신용손실(ECL)

차주 신용점수, 기존 DTI·DSR, 연체·납부 이력, LTV, 기존 담보를 사용해 설명 가능한 12개월 PD와 LGD를 산출한다. 정상 상태에는 12개월 ECL, 연체·상환위험 급증 등은 계약기간 ECL을 적용한다. 국가별 낙관·기준·하방 시나리오의 확률과 PD/LGD 배수는 `credit_risk_scenarios`에서 조정한다. 일별 평가를 `loan_ecl_assessments`에 보존하고, 충당금 증감은 기존 `financial_institution_ledger`를 통해 기관 자기자본에 반영한다. 부도 시 기존 충당금과 실제 회수 후 손실의 차이만 손익에 반영한다.

기대손실은 계약 유효이자율(없으면 계약금리, 둘 다 없으면 상품금리)로 할인한다. Stage 1은 향후 12개월 또는 잔여 계약기간 중 짧은 쪽의 중간, Stage 2는 잔여 계약기간 중간, Stage 3는 부도 후 회수기간을 1년으로 둔 중간 시점(6개월)을 예상 손실 시점으로 삼는 투명한 proxy다. Stage 1·2는 그 중간 시점 전에 납부 예정인 미도래 상환회차의 미납 원금을 현재 잔액에서 차감해 EAD를 추정하며, 상환 일정이 없거나 Stage 3이면 현재 잔액을 쓴다. 평가 행/시나리오에 적용 EIR, 예상손실 시점, 할인계수, EAD 방법을 보존해 관리자 웹에서 확인할 수 있다. 다중 시점 부도확률·현금흐름 가중, 미납회차의 실제 회수시점, 미래 인출·한도대출은 모델링하지 않는다.

관측 거시지표는 scorecard PD에 다음 시뮬레이터 배수를 먼저 적용하고, 이후 국가별 시나리오 배수를 적용한다: `clamp(1 − 0.08 × (GDP성장률 − 2) + 0.04 × (실업률 − 5) + 0.02 × (물가상승률 − 2), 0.5, 2.5)`. 단위는 모두 퍼센트포인트다. 이 계수는 명시적·설명 가능한 게임 모델 입력이지, 실제 경기 민감도 추정치가 아니다. 전망경로, 거시변수 간 상관과 차주별 민감도는 아직 없다.

이 1차 모델은 시뮬레이터용 점수카드다. 감독기관 승인 모델이나 실제 신용평가 모형으로 간주하지 않는다. 평가 기록은 보존되고 충당금 증감은 기관 손익원장과 은행 분개장에 연결되며, 뒤의 거시 시나리오·모형 검증 작업에서 입력을 정교화한다.

- ECL 시나리오 편집은 낙관·기준·하방 확률의 합이 1인 경우에만 저장한다. 서버가 같은 조건을 강제하고, 웹 입력도 저장 전에 검증한다. 이전 버전에서 저장된 양수 가중치는 평가 결과를 보존하도록 비율을 유지한 채 시작 시 합계 1로 정규화한다.
- 기대신용손실을 계약 유효이자율로 할인하고, Stage 1·2는 잔여기간, Stage 3는 1년 회수기간 가정의 midpoint를 적용한다. 사용 EIR·예상손실 시점·할인계수를 append-only 평가 이력 및 준법 대시보드에 기록한다. 이는 할인된 현금흐름 기반 IFRS 9 모델이 아니라 더 단순한 시뮬레이터 근사다.
- 국가별 물가상승률·실질성장률·실업률은 조달/은행채 압력에, 재정 부채비율은 국채 압력에 제한된 계수로 반영한다. 입력·변경감사는 관리자 국가 웹 화면에서 보며, 기준금리 결정은 자동화하지 않는다. 전망치·기대·국가 간 파급·시장 체결로부터 내생적으로 만들어지는 거시 경로는 아직 없다.
- 다른 통화를 쓰는 타국의 평균 기준금리와 국내 정책금리의 차이를 조달/은행채 압력에 10% 민감도, 국채 압력에 절반 민감도로 더하며 ±2%p로 제한한다. 관리자 웹에서 기준 참조값과 현 가산을 조회한다. 동일 통화권은 제외하고, 다른 통화국은 동일 가중 평균만 쓰며 국가 위험·환헤지·실제 국경간 자금흐름을 측정하지 않는다.
- 30일 유동성 민감도에 통화 환산 예금액 기준 최대 예금자 및 상위 5명 잔액 비중을 추가했다. 다중계좌는 사용자별로 합산하지만 보험한도 초과분·예금행동 분류·동시 인출 확률을 반영하지 않으므로 LCR 산출은 아니다.
- 국가별 물가·실업·성장 관측치로 ECL scorecard의 12개월 PD에 제한적 거시 배수를 먼저 적용하고 기간 PD 및 시나리오 기대손실에 전달한다. 산출 시 거시 배수를 별도 평가 칼럼과 시나리오 JSON에 보존하고 웹에 표시한다. 계수는 보정되지 않은 시뮬레이터 가정이며, 거시전망·차주별 민감도·부도상관은 미구현이다.
- 부도 상태 대출도 ECL 대상에 포함하고 Stage 3 및 100% 부도확률로 분류한다. 이는 시뮬레이터 정책이며 회계기준 승인 모델은 아니다.
- 연체 시작시각이 있는 대출은 30일 이상 연체를 Stage 2의 연체 기준으로 사용한다. 초기 연체는 PD scorecard에 연체 가산요인으로 남고, 2회 이상 미납·LTV 100% 이상은 별도 Stage 2 트리거다. 과거 레코드처럼 연체 시작시각이 없는 경우에는 보수적으로 기존 Stage 2 분류를 유지한다. 이는 30일 연체 SICR 실무 관행을 단순화한 근사이며 정성적 유의적 신용위험 증가 판단이나 반증 가능 규칙은 아직 없다.
- 신규 대출은 심사 시점의 거시조정 12개월 PD를 취급 기준값으로 저장한다. 이후 같은 scorecard의 최신 PD가 취급 시점 PD의 2배 이상이면 Stage 2로 분류하며, 구형 대출은 기준 PD가 없으므로 이 비교를 생략한다. 이는 상대적 신용위험 악화를 반영하는 설명용 SICR trigger다. 신용등급 전이, 만기별 PD term structure, 정성적 판단, 국가별 규제 매개변수는 미구현이다. 사용자 HTS 대출 일정에 취급 PD와 최신 ECL Stage/PD를 표시한다.
- Stage 2 원인이 해소된 첫 평가부터 개선 관찰시각을 대출에 저장하며, 그 뒤 90일 이상 지난 평가에서 Stage 2 트리거가 없을 때 Stage 1로 복귀한다. 그 사이 어떤 Stage 2 트리거든 재발하면 관찰기간을 초기화한다. ECL 평가 사이의 미관측 기간 중 잠재적인 위험 변화는 알 수 없으므로, 이 값은 시뮬레이터의 투명한 cure 정책이지 국제 기준의 일률적인 의무기간이 아니며 국가별 설정도 아직 없다.
- Stage 1·2 EAD는 예상 손실 midpoint까지 예정된 미도래 원금 상환을 반영해 추정하고, Stage 3·상환일정이 없는 대출은 현재 잔액을 사용한다. 이는 고정 회차상환 대출을 위한 단일 시점 proxy이며, 미래 인출·한도사용·부도 시점 분포를 반영한 EAD 모형은 아니다.
- 고정금리 대출의 예정 원금상환과 정기예금의 잔여만기를 금액가중한 1·2차 시간 모멘트로 통화별 ±100/200bp 2차 ΔEVE proxy를 계산한다. 요구불예금은 0 duration, 무만기 대출은 제외하고 건수를 드러낸다. 이는 현금흐름 할인으로 구한 실제 컨벡서티가 아니며 쿠폰 PV·시장수익률곡선·증권·파생·행동성 예금/선택권은 미포함이므로 감독 IRRBB 또는 실제 경제가치 평가가 아니다.
- 관리자 은행 원장 웹 화면에 대출 상환스케줄의 미수금은 각 납부일, 스케줄 밖 잔여 원금은 계약 만기일에 배치하는 통화별 계약상 만기갭(1·7·30·90·365일 및 초과)을 추가했다. 예금은 계약기간 만기 유출로 둔다. 이는 대출 유입과 예금 유출의 단순 ALM 보조지표다. 행동만기·조기인출·장부외 흐름·시장성 자산/조달·LCR/NSFR은 포함하지 않으며 규제비율이 아니다.
- 계약상 만기갭 보고서는 통화별 최소단위로 유입·유출을 반올림한 뒤 구간 및 누적 갭을 계산한다. 따라서 레거시 REAL 잔액이나 소수 잔여값이 무소수 통화(JPY 등)의 하위 최소단위로 관리자 보고서에 노출되지 않는다. 원천 DB 전체의 Decimal 전환을 뜻하지는 않는다.
- 관리자 은행 원장 웹에서 예금보험 청구의 covered/uninsured 금액과 각각의 분개장 부채 계정을 상품통화 최소단위로 대사한다. 누락·차이는 읽기 전용으로 표시하며 자동 분개하지 않는다. 이는 보험기금의 재원·지급능력이나 법정 손실순위를 검증하지 않는다.
- 일반 예금은 개설·해지 왕복 흐름에서 고객 현금, 예금부채, 은행 분개 균형과 잔액 대사가 닫히는 통합 회귀 테스트를 추가했다. 이는 전체 예금 회계 경로가 완성됐다는 뜻은 아니며, 기존·미연결 이벤트는 계속 별도 대사 대상이다.
- 예금보험 청구 이력에 원예금 통화의 보장·미보장액과 실제 고객 지급 통화·금액을 함께 보존해 HTS와 관리자 웹에서 나란히 확인한다. 과거 행은 실제 지급 통화/금액이 미기록 상태로 남으며, 국가 간 지급액 환산은 지급 당시 환율 기준이다. 별도 보험기금 잔액·보험료·대위권 회수는 아직 없다.
- 같은 화면에 통화별 10%·25%·50% 예금 인출 가정의 1일 순갭 민감도를 추가했다. 기존 1일 계약상 예금 유출과 가정 인출액 중 큰 값을 비교하며, 현금·준비금·매각가능자산을 모델링하지 않으므로 실제 유동성 부족이나 생존 가능성을 판정하지 않는다.
- 관리자 은행 보고서에 예금 5/10/20/40% 이탈 시나리오별로 현금·준비금 대용치와 30일 내 정상 대출상환 예정액의 50%를 적용한 커버리지 민감도를 추가했다. 유가증권 HQLA·담보·규제 헤어컷·행동만기·장부외 흐름을 제외한 설명용 proxy이며 LCR이나 실제 생존기간이 아니다.
- 30일 유동성 민감도에 실제 예금 계좌만 포함한 예금자 집중도와 사용자별 미보장 예금 잔액 proxy를 추가했다. 외화 예금은 통화별 기관 총액을 먼저 합산해 기준통화로 환산하고, 사용자별 외화 잔액은 통화별로 합산해 최대 예금자 노출과 상위 5명 잔액 비중을 관리자 웹 화면에 표시한다. 상품의 보험 대상 플래그와 기관의 사용자별 보장 한도를 단순 적용하며, 최대 예금자 또는 상위 5명이 전액 인출하는 별도 순유출·커버리지 민감도도 제공한다. 인출 확률을 추정하는 모델이 아니며, 법인/소매행동 구분·국가별 합산 법률은 아직 반영하지 않는다.
- 관리자 은행 보고서에 정상 대출 포트폴리오의 5/10/20/40% pro-rata 동시부도 시나리오를 추가했다. 기존 담보조정 LGD와 충당금의 비례 사용을 반영해 EAD·총손실·추가충당금·충당 후 자기자본을 표시하며 대출/회계 상태는 변경하지 않는다. 상품통화별로 먼저 합산한 뒤 기관 기준통화로 환산해 소액 외화 잔액의 건별 반올림 소실을 방지한다. 차주선택·부도상관·거시 피드백·회수 시점이 없는 단순 스트레스다.
- 관리자 은행 보고서에 변동금리 대출·예금의 다음 재산정일부터 계약 만기까지의 잔액-연도를 합산하고, ±100/200bp 평행충격의 향후 1년 이자수익·비용·순이자수익 변화를 통화별로 표시한다. 계약 금리하한·상한의 비대칭 효과를 적용하지만 전액 지표금리 전가, 잔액 유지 가정이며 상환, 예금 베타, 헤지·베이시스 효과, 법정 최고금리 재산정은 제외하므로 IRRBB 규제 측정치가 아니다.
- 은행 자본용 대출 RWA를 일괄 75% 대신 담보·신용상태 구간으로 계산한다: 현금담보 0%, 자산담보는 20% 할인 후 35%, 정상 무담보 75%, 고위험(Stage 2/낮은 점수/높은 LTV/연체) 무담보 100%, 부도 무담보 150%. EAD·담보·가중노출을 상품통화 정밀도로 계산하고 외화 익스포저는 통화별 가중노출을 먼저 합산한 뒤 기관 기준통화로 환산해 최소단위 반올림에서 소액 건이 사라지는 것을 방지한다. 자본여력·기관 상태 제한에 이 RWA를 사용하지만, 이는 명시적 시뮬레이터 가정이며 실제 Basel 표준방법 구현이나 법정 자본비율 계산이 아니다.
- 신규 대출 자본여력도 신청자의 현금·자산담보와 신용점수에 맞춘 같은 0%/35%/75%/100% RWA 혼합가중치로 산정한다. 기존처럼 신규 대출을 무조건 75%로 간주해 담보대출 자본여력을 왜곡하지 않으며, 부도 150% 가중치는 취급 전 신규 계약에는 적용하지 않는다.
- 유효 자기자본 ÷ (대출 포함 예금성 부채 + 자기자본)의 간이 익스포저비율에 3% 하한을 두어, RWA 자본제약과 별도로 신규 대출 여력 및 기관 제한에 반영하고 관리자 원장 화면에 표시한다. Tier 1 자본 분류와 오프밸런스 익스포저가 없는 시뮬레이터 가정이며 Basel 레버리지비율로 간주하지 않는다.

- #80 관리자 거절 경로를 추가했다. 허용 코드(`compliance_review`, `invalid_program`, `insufficient_custody`, `operational_error`, `other`)만 받으며, 관리자 행위 로그와 요청 이벤트의 `detail_code`에 근거를 기록하고 수량 예약을 원자적으로 해제한다. 잘못된 코드로 상태가 바뀌지 않고, 유효 거절 뒤 상태·이벤트·예약 해제가 일치하는 manager/API 테스트를 추가했다. 관련 테스트 57개 및 subtests 31개와 API·대시보드 빌드가 통과했다.
- #80 관리자 웹의 읽기 전용 custody reconciliation을 추가했다. DR별 순발행량과 현재 보유량, 이동원장의 예탁 원주수량과 전환비율 기대수량, 활성 요청과 미해제 예약, 요청 최종 상태와 append-only 이벤트의 일치, 사용자 보유 대비 예약 초과를 검사한다. 차이는 DR 프로그램별·요청별로 보여주며 자동 조정하지 않는다. 정상 원장/의도적 보유량 불일치 및 관리자 API 감사 테스트 포함 59개 통과, subtests 31개 통과; API·dashboard 빌드와 Python compileall 및 diff check도 통과했다. 이 검사는 수수료/현금 분개 대사나 전체 시장 주문·대출 담보 통합 초과예약을 증명하지 않는다.
- #80 M2 운영·수수료 잔여 항목을 구현했다. 정산 가능 시각 24시간 경과는 관리자 대시보드 경고로, 7일 경과는 `expired_unsettled` 거절·예약 해제로 처리한다. DR별 발행/상환 bp 수수료는 상품 웹 고급설정에서 조정하며 요청 시점의 비율·가격·호가통화를 스냅샷한다. 정산 시 해당 quote currency 통화예금 계좌에서 상품 통화 최소단위로 half-up 반올림해 차감하고, 별도 불변 fee ledger 및 `DR_CUSTODY` BankJournal에 기록한다. 관리자 custody 대사는 수수료 원장과 수익 분개 총액도 비교한다. fee 부족 시 자산이동·수수료·분개 모두 원자 롤백한다. 관련 65 tests / 31 subtests, API·dashboard·HTS 빌드, compileall 및 diff check 통과. 실행 프로세스 중단 동안 만료/정산 worker는 실행되지 않으며 재기동 뒤 처리된다. 계획상 M2의 모든 항목을 완료했다. 이는 내부 수탁 시뮬레이션이며 실제 수탁기관·외부 결제기관 연결은 아니다.
- #80 M3 국경간 배당·원천징수와 후속 세 제한 해소를 구현했다. 동일 원주/통화로 지급되는 원주 및 여러 DR 프로그램을 각각 지급행으로 분리하고, DR별 주주명부 기록 시점에 고정한 수익자 세무거주지·국적·상장/기초주 관할·기준일로 각자 유효 규칙을 선택한다. HTS 지갑에서 사용자가 세무거주지를 자기신고하고 변경 내역은 append-only 이벤트로 남긴다. 관리자 웹은 규칙 이력, 프로그램별 최근 지급, 통화별 gross-tax-net 최소단위 대사와 배당 복식부기 차변/대변 대사를 제공한다. 배당 지급 및 세금 국고 송금은 `BankJournal`에 상품통화 최소단위로 기록하며 DB 변경과 원자 처리한다. 과거 지급행은 `allocation_key='legacy'`로 보존하는 호환 마이그레이션을 포함한다. 규칙/원천징수 이벤트/세무거주지 변경 이벤트는 갱신·삭제를 막고 관리자 API 접근/추가는 감사 로그에 남긴다. 최종 통합검증은 764 passed / 618 subtests, 종료 시그널 테스트 2 passed, API/dashboard/HTS/site 빌드, compileall, diff check 통과다. 승인된 범위 밖 제한은 자기신고 거주지 증빙·법률 판정, 실제 조세조약 데이터·신고·송금, 외부 수탁기관 연결이다. #80 내부 시뮬레이터 범위 완료.
- 신용점수를 직접 차감하던 방식을 append-only 신용 이벤트 원장 기반 재계산으로 바꿨다. 연체·기한이익상실·부도 기록은 반감기로 감쇠하고 보존기간 후 소멸하며, 정상 납부·완납·미납 회차 사후 납부가 점수를 회복시킨다. 관리자 정정은 사유와 처리자가 남는 조정 이벤트이고, 모델 밖 수정은 다음 계산 때 흡수한다. 도입 시점 점수는 보정값으로 보존하되, 모델보다 낮은 차이만 감쇠한다. 계수는 보정되지 않은 시뮬레이터 가정이다.
