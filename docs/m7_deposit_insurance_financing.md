# 예금보험 정리 지급의 자금 출처 (M7)

## 문제
`BankManager.resolve_failed_institution`은 실패한 은행의 보험 대상 예금을 예금자에게 지급할 때 항상 **국고 지갑을 차감**한다(`CurrencyManager.treasury_pay`). 예금보험기금 원장(`deposit_insurance_fund_events`)과 국고 보전(`deposit_insurance_backstops`)을 같은 흐름에 얹으면 같은 청구가 국고에서 두 번 차감될 수 있었다(기금 지급 기록 후 부족분을 국고로 다시 보전).

## 정한 흐름: 기금이 먼저 부담하고, 부족분만 국고
관할 플래그 둘은 모두 기본 꺼짐이다.

| 기금 자동 기록 | 국고 보전 | 청구 하나의 지급(P) |
|---|---|---|
| 꺼짐 | 꺼짐 | 국고가 P 전액 지급. 기록 없음(기존 동작 그대로) |
| 꺼짐 | 켜짐 | 위와 같음(국고 보전만 켜도 정리 지급은 바뀌지 않는다) |
| 켜짐 | 꺼짐 | 기금이 `min(P, 기금 잔액)`을 부담하고 국고는 나머지만 지급. 기금 지급 이벤트는 기금 부담분만 기록 |
| 켜짐 | 켜짐 | 위와 같은 지급. 기금 지급 이벤트는 P 전액, 국고가 낸 나머지는 같은 크기의 보전 기록으로 남겨 기금 잔액 변화는 `-기금 부담분`이 된다 |

- 청구별 자금 출처는 추가 전용 표 `deposit_insurance_claim_funding`(지급액 = 기금 부담 + 국고 지급)에 남는다. 기금 자동 기록이 꺼져 있으면 이 표에는 아무것도 쓰지 않는다.
- 정리가 기금 잔액을 음수로 만들지 않는다. 같은 청구에 대한 이벤트·보전 기록은 키(`claim:<id>`, `resolution-claim:<id>`)가 유일해 재실행해도 늘지 않는다.
- 관리자가 수동으로 청구 지급을 기록하는 동작(`record_claim_payouts`)은 이미 자금 출처가 기록된 청구를 건너뛴다. 정리 때 국고가 전액 낸 옛 청구를 수동 기록하더라도 `cover_shortfall`의 보전 대상에서 빠진다(이중 차감 방지).
- 국고 보전 한도(관리자 지정)는 정리 중에는 감시값이다. 예금자 지급을 멈출 수 없으므로 한도를 넘어도 지급은 진행하고 대사에서 초과로 드러난다. 한도는 관리자가 직접 실행하는 `cover_shortfall`에는 강제된다.

## 증거
- `tests/test_m7_deposit_insurance.py::FundAutoRecordTests`: 두 플래그 네 조합에서 국고 차감 합계 = 지급 − 기금 부담, 기금 잔액 0 미만 없음, 대사 일치, 재실행 불변.
- 운영 복사본(자기 이름 DB, 읽기 전용 `pg_dump`)에서 정리 시뮬레이션: 은행 하나에 5,000을 예금으로 두고 두 플래그를 켜고 보험료 1,500을 징수한 뒤 정리하면 기금 1,500, 국고 3,500이 지급되고 기금 잔액 0, 은행 분개(고객예금·보험금지급채무)와 청구 대사가 모두 일치했다.
- 운영 복사본에서 발견한 것: PostgreSQL 스키마 동기화는 표만 만들고 시드 행을 넣지 않아 기존 DB에는 은행 계정과목 `deposit_insurance_premium_expense`가 없다. `collect_premium`이 첫 실행 때 이 계정을 보충한다(`INSERT OR IGNORE`). 새 표의 금액 등록부 행은 `docs/m8_prod_migration_runbook.md`의 등록부 이관 절차를 따른다.
