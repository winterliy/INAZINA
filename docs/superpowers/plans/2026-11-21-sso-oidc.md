# Unified SSO (OIDC IdP) and Caddy Front Door Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `id.inazina.kr` becomes an OIDC identity provider (code + PKCE); naru (HTS) and console (dashboard) sign in through it; `infra/Caddyfile` is the only public entry.

**Architecture:** The IdP is a module inside the existing Node API (4312) built on `node-oidc-provider`, mounted at `/oidc`. Its state lives in a new Python-side table reached through internal endpoints. Each app's API process acts as the relying party: it runs the code exchange on `/api/auth/oidc/*`, verifies the ID token, then issues the existing host-only `inazina_session` cookie, so per-request role and `authVersion` checks stay unchanged.

**Tech Stack:** Node 24 + TypeScript (tsx, `node --test`), `node-oidc-provider`, `openid-client`, Python `web_api` + pytest, Caddy 2.

**Spec:** `docs/superpowers/specs/2026-11-21-sso-design.md`

## Global Constraints
- Authorization code + PKCE `S256` only; no implicit flow, no wildcard redirect URIs.
- Scopes `openid profile`; claims `sub`, `name`, `role`, `auth_version`.
- `api.inazina.kr` and port 4313 must never appear as a Caddy site or upstream.
- `wl.kr` (4315) keeps its own login; not an OIDC client.
- Emergency passcode and the 4312/4313 browser-access gate are unchanged.
- Dependency versions pinned exactly (no `^`); get them with `npm view <pkg> version` at install time and run `npm run typecheck && npm run build`.
- Passwords stay scrypt in the existing store; the IdP never stores plain text.
- Edit directly in `~/Desktop/inazina`; push to master, no PRs or extra branches.
- Replies and UI copy for the user in Korean; match existing Korean login copy.

## Review Focus
1. Open redirect: `redirect_uri` or `post_logout_redirect_uri` not exactly registered → rejected, never redirected.
2. Replayed or stolen authorization code, or wrong `code_verifier` → token exchange fails.
3. Tampered ID token (bad signature, wrong `iss`/`aud`/`nonce`, expired) → no session issued.
4. Password changed at the IdP → existing app sessions end (`authVersion` mismatch → `session_expired`).
5. IdP down or database down → app shows a login error, not a loop of redirects; emergency gate still opens.
