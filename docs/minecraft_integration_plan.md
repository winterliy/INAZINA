## 전제와 선행 조건

- 웹 내부 서비스의 아이템 시스템(개체 ID, 소유자, 위치, 버전)과 서비스 계층 분리가 먼저 있어야 한다. 경계 약속은 consumption_plan.md의 "마인크래프트 연동과의 경계"를 따른다.
- PostgreSQL 전환이 선행되어야 한다. SQLite 파일은 서버 간 공유에 맞지 않는다.
- 웹 내부 서비스는 Milestone 프로젝트(M4, M6–M8)가 모두 끝난 뒤 착수한다. 이 연동은 그 웹 서비스가 만들어진 뒤에 시작하므로, 그때까지 이 문서도 기획 상태로 대기한다. 웹 쪽에서 보류한 결정(강화 효과 용처 등)이 정해져야 아이템 능력치 연동을 설계할 수 있다.
- 웹은 HTS를 우선한다. 인게임 GUI는 웹과 같은 기능을 쓰되, 웹 화면이 먼저 완성돼 있어야 따라 만들 수 있다.

## 경제 시간 (INAZINA 시간 = 마인크래프트 서버 시간)

확정: 앞으로 INAZINA 시스템의 시간 단위는 마인크래프트 서버 내 시간을 따른다. 이 결정은 이 연동만이 아니라 이자, 만기, 거래 시간 등 기존 시스템 전반에 영향을 주므로 가장 먼저 설계한다.

### 기본 환산

마인크래프트의 하루는 24,000틱이며 20TPS에서 현실 20분이다. 이를 그대로 쓰면 다음과 같다.

| 마인크래프트 시간 | 현실 시간 |
|---|---|
| 1일 | 20분 |
| 1월(30일) | 10시간 |
| 1년(365일) | 약 5.07일 |

### 영향 범위

대출·예금·적금·채권·ELS·옵션·선물 만기, 이자 계산(ACT/360, ACT/365), 시장 거래 시간, 쿨다운, 임시계좌 30일 보관, 출석의 날 경계, 월세·재산세, 실적 분기. 이 중 현재 코드가 현실 시각(`time.time()` 등)을 직접 쓰는 곳이 많아, 시간 조회를 한 모듈로 모으는 작업이 선행되어야 한다.

### 풀어야 할 문제

1. **틱 지연:** TPS가 떨어지면 게임 시간이 현실보다 느리게 흐른다.
2. **서버 정지:** 서버가 꺼지면 게임 시간이 멈춘다. 웹·HTS·디스코드는 서버와 독립으로 동작해야 하는데 이때 시간은 어떻게 되는가.
3. **시간 조작:** `/time set`, 침대 수면으로 밤 건너뛰기, 낮밤 주기 규칙(`doDaylightCycle`)으로 시간을 가속·정지시켜 이자를 앞당기거나 만기를 피할 수 있다.
4. **진행 중인 계약:** 이미 현실 시간 기준으로 맺은 대출·예금 만기를 어떻게 전환하는가.

### 권장안: 경제 시계

서버의 시간 값을 직접 쓰지 않고, 별도의 **경제 시계** 모듈을 둔다.

- 경제 시계는 현실 시간에서 경제 시간으로 환산하는 단조 증가 함수다(1 경제일 = 현실 20분 고정 비율, 설정값).
- 마인크래프트 서버는 이 시계를 표시하고 동기만 한다. 플러그인이 하늘의 시간을 경제 시계에 맞춰 줄 수 있다. 수면·명령으로 시간을 바꿔도 경제 시간에는 영향이 없다.
- 서버가 꺼져도 경제 시계는 흐른다. 대출 만기, 선물 마진콜 같은 금융 사건이 서버 가동 여부에 묶이지 않는다.
- 웹과 마인크래프트가 항상 같은 시각을 본다.

대안은 서버가 가동한 틱을 합산하는 방식이다. "서버 내 시간"에 더 충실하지만, 서버 정지 중 금융이 멈추고 시간 조작 악용을 막기 어렵다.

### 전환 순서(제안)

1. 시간 조회를 한 모듈(`time_utils` 등)로 모은다. 이 단계는 동작을 바꾸지 않는다.
2. 경제 시계 모듈을 도입하되 처음에는 현실 시간과 같게 둔다.
3. 환산 비율과 전환 시점을 정한다. 전환 시점에 진행 중인 계약의 잔여 기간을 새 단위로 변환하는 규칙을 적용한다.
4. 마인크래프트 서버와 동기화한다.

## 연동 설계

뽑기 또는 쇼핑몰에서 구매한 아이템을 마인크래프트 서버에서 쓰고, 강화 시스템도 서버 연동을 전제로 구축할 예정이다. 서버는 Paper 계열(GLAP1 포크 또는 별도 플러그인)을 가정한다. 구현 때는 [Paper API Javadoc](https://jd.papermc.io/paper/26.3/)을 확인한다. 지금 단계의 목표는 연동 자체를 만드는 것이 아니라, **인게임 아이템과 1:1로 대응할 수 있게 아이템·강화 설계를 처음부터 엔진 중립으로 잡는 것**이다.

### 핵심 원칙

1. **원장은 INAZINA가 단일 진실 공급원이다.** 아이템 소유, 강화 단계, 거래 이력은 INAZINA DB가 갖고, 마인크래프트의 아이템은 그 사본을 표시하는 것으로 본다. 서버가 아이템을 직접 만들어 내지 않는다.
2. **복제 방지가 최우선이다.** 같은 아이템이 웹과 인게임에 동시에 존재하면 안 된다. 아래 상태 기계로 한 시점에 한 곳에만 존재하게 한다.
3. **서버가 꺼져도 경제는 동작한다.** 연동은 INAZINA 쪽 큐(outbox)에 쌓고, 플러그인이 가져가는 방식이라 서버 점검과 무관하게 구매와 강화가 진행된다.
4. **강화의 권한은 INAZINA에 둔다.** 인게임 강화 화면은 INAZINA API를 호출하는 창구일 뿐이다. 확률과 비용 계산, 난수는 항상 INAZINA 서버가 한다.

### 계정 연동

- 웹/디스코드 계정과 마인크래프트 UUID를 연결한다. 인게임에서 `/link`로 일회용 코드를 받고 HTS/디스코드에서 입력하는 방식을 권장한다.
- 계정 하나에 UUID 하나가 기본이다. 변경은 재인증과 대기 기간을 둔다.
- 연동 전에는 구매와 강화는 가능하지만 인게임 전달은 보류 상태로 둔다.
- 정식 계정(온라인 모드) 서버를 전제로 한다. 오프라인 모드면 UUID를 신뢰할 수 없다.

### 아이템 정의에 미리 넣을 필드

아이템 시스템의 정의 테이블에 아래 필드를 처음부터 둔다. 지금은 비워 두어도 된다.

| 필드 | 용도 |
|---|---|
| `mc_material` | 인게임 베이스 아이템(예: 다이아몬드 검) |
| `mc_custom_model_data` / 리소스팩 키 | 외형(리소스팩) |
| `mc_attributes` | 강화 단계별 공격력·방어력 등 속성 수정치 |
| `mc_tradeable_in_game` | 인게임 드롭·거래 허용 여부 |
| `mc_delivery_mode` | 전달 방식(우편함 / 즉시 지급 / 웹 전용) |
| `mc_enabled` | 마인크래프트 서버에서 사용 가능한지 |
| `rarity` (웹 공통) | 희귀도 등급. 바닐라 아이템 정의에도 둔다 |
| `base_price` / `price_model` (웹 공통) | 기준가와 가격 모델 설정. 바닐라 아이템 정의에도 둔다 |

개체별로는 아이템 ID(UUID), 강화 단계, 내구도, 소유자를 저장한다. 인게임 아이템에는 `PersistentDataContainer`로 아이템 ID와 강화 단계, 서명 값을 심어, 서버가 위조된 아이템을 가려낼 수 있게 한다.

### 확정 사항 (2026-11-18)

- **양방향 연동:** 웹과 인게임 모두에서 같은 아이템을 부를 수 있다. 웹 → 인게임 지급, 인게임 → 웹 회수를 모두 지원한다.
- **같은 DB를 공유한다.** 웹과 마인크래프트 서버가 하나의 DB를 단일 진실 공급원으로 쓴다. 이를 위해 PostgreSQL 전환(진행 중) 후 연동을 진행하는 것을 전제로 한다. SQLite 파일은 서버 간 공유에 맞지 않는다.
- **사망 시 유품상자(확정):** 사망한 자리에 큰상자(더블 체스트)를 설치해 유품상자로 만든다. 소지 아이템의 소유권은 소멸해 무주 상태가 되고, 상자에서 꺼내 가면 꺼낸 사람이 새로 취득한다(재취득 가능). 소멸과 재취득은 모두 이력(사유 `death`, 시각, 좌표, 월드)을 남기는 기록이다. 세부는 아래 "유품상자".
- **플러그인 권한 (확정):** 플러그인은 DB를 **읽기만 자유롭게** 하고, **수정은 제한된 DB 역할로 허용된 동작만** 한다.
- **기능 범위 (확정):** 인게임에서도 웹과 같은 기능을 쓸 수 있게 한다. 단, 화면과 입력 방식은 인게임에 맞게 GUI로 만든다.
- **이동 규칙 (확정):** 인게임 → 웹으로 보내면 아이템이 인게임에서 제거되고 웹 보관함으로 간다. 웹 → 인게임으로 보내면 인게임 인벤토리에 아이템이 지급된다.
- **인벤토리 인식 (확정):** 플러그인이 유저의 인벤토리를 인식해 INAZINA 아이템을 DB와 맞춘다(아래 참고).
- **웹 보관함 (확정):** 마인크래프트 아이템(바닐라 아이템과 INAZINA 아이템 모두)을 인벤토리에서 웹에 올려 보관하다가 다시 꺼내 올 수 있다. 세부는 아래 "웹 보관함".
- **희귀도와 실시간 가격 (확정):** 바닐라 아이템과 INAZINA 아이템 모두에 희귀도와 실시간 가격을 부여한다. 세부는 아래 "희귀도와 실시간 가격".
- **서버는 Paper 기반이다.** GLAP1 포크 또는 Paper 플러그인으로 구현한다. API는 Paper Javadoc(https://jd.papermc.io/paper/26.3/)을 확인한다.
- **범위:** 아이템만이 아니라 현재 INAZINA의 모든 시스템을 마인크래프트 서버와 연동할 예정이다. 구상은 아래 "전 시스템 연동 구상"에 둔다.

### 같은 DB 공유 시 설계 (복제 방지)

같은 DB를 공유하면 사본을 전달하는 방식보다 **소유권 행 하나가 진실**이 되는 방식이 단순하고 안전하다.

- 아이템 개체 행에 `owner`, `location`(웹 보관 / 인게임 소지 / 인게임 보관함), `version`(낙관적 잠금용)을 둔다.
- 인게임 아이템은 그 행을 가리키는 **표시물**이다. `PersistentDataContainer`에 아이템 ID와 서명 값을 넣고, 사용·줍기·접속·월드 이동·거래 시점에 DB 소유권과 대조한다. 행이 없거나 소유자가 다르면 아이템을 제거한다.
- 웹 → 인게임: `location`을 인게임 소지로 바꾸는 한 번의 트랜잭션 + 지급 확인. 인게임 → 웹: 아이템 제거와 `location` 변경을 한 번에 처리한다.
- 소유권 변경은 모두 `version` 비교로 중복 요청을 막고, 요청마다 멱등 키를 둔다.
- 사망 처리: 플러그인이 사망 이벤트에서 그 플레이어의 INAZINA 아이템 행을 무주 상태(`location`=유품상자)로 바꾸고, 일반 드롭을 막은 뒤 유품상자에 담는다. 무주 전환과 재취득 기록은 아이템 총량 대사에 포함한다.
- 서버 크래시, 롤백, 관리자 명령(`/give`)으로 생긴 아이템은 DB에 행이 없으므로 접속·사용 시 대조에서 걸러진다.
- 미확인 상태가 오래되면 자동으로 되돌리지 않고 관리자 대시보드에 표시한다.

### 인벤토리 인식과 이동

- **인식 시점:** 접속, 주기(수 초~수십 초), 인벤토리 변경·아이템 줍기/버리기/상자 이동, 월드 이동, 사망, 종료.
- **식별:** 인게임 아이템의 `PersistentDataContainer`에 아이템 ID와 서명이 있어야 INAZINA 아이템으로 본다. DB 소유자와 인벤토리 주인이 같은지 확인한다.
- **대조 결과:** DB에 소유 기록이 있고 일치하면 그대로 둔다. 기록이 없거나 소유자가 다르거나 서명이 틀리면 제거하고 관리자 로그에 남긴다. `location`은 `인게임 소지`로 유지한다.
- **웹으로 보내기(인게임 → 웹):** 플레이어가 GUI에서 보내기를 고르면 인게임 아이템을 제거하고 `location`을 `웹 보관`으로 바꾼다. 제거 확인 후에만 웹 보관으로 바뀐다.
- **인게임으로 보내기(웹 → 인게임):** 웹에서 보내기를 고르면 `location`이 `인게임 전달 대기`가 되고, 플레이어가 접속 중이면 즉시, 아니면 접속 시 지급한다. 지급 확인 후 `인게임 소지`로 바뀐다. 인벤토리가 가득 차면 인게임 보관함으로 보낸다.
- **상자·드롭·거래:** 상자에 넣는 것은 `인게임 보관함`으로, 다른 플레이어가 줍거나 거래하면 소유권 이전 규칙(웹 거래와 같은 경로)을 거친다. 소유자가 아닌 플레이어가 줍는 것을 막을지는 결정 사항에서 정한다.

### 유품상자 (사망 처리)

- **설치:** 사망한 자리에 큰상자(더블 체스트)를 설치해 소지 아이템을 담는다. 인벤토리 슬롯(보조 손·갑옷 포함)이 54칸 이하라 한 개에 들어간다.
- **소유권:** 담긴 INAZINA 아이템은 소유권이 소멸해 무주 상태가 된다. 상자에서 꺼내 가는 순간 꺼낸 사람이 새 소유자가 되고(재취득), DB 소유권 이전과 함께 기록한다.
- **DB 기록:** `유품상자` 행(위치, 월드, 사망자, 생성 시각, 내용 스냅샷)을 두고, 상자 안 INAZINA 아이템 행의 `location`을 `유품상자`로 둔다.
- **위치 대체:** 사망 지점이 허공, 용암, 물, 월드 경계, 보호 구역(부동산 필지 등)이라 설치할 수 없으면 가까운 안전한 위치로 옮기고 사망자에게 좌표를 알린다.
- **보호:** 호퍼 추출과 폭발·피스톤 파괴를 막아, 상자를 통한 복제나 소실이 생기지 않게 한다. 상자가 어떤 이유로든 사라지면 내용물은 DB 기준으로 처리한다(아래 결정 사항).
- **서버 장애:** 크래시나 재시작 중 사망해도 유품상자 행이 먼저 기록되도록 순서를 정하고, 접속 시 대조해 상자와 DB가 어긋나면 복구한다.

### 웹 보관함 (인게임 ↔ 웹, 바닐라 포함)

- **올리기:** GUI에서 인벤토리의 아이템을 골라 웹 보관함에 올린다. 아이템이 인벤토리에서 제거되고 웹 보관 수량에 더해진다.
- **꺼내기:** 웹 또는 인게임 GUI에서 수량을 골라 꺼내면 인벤토리에 지급된다. 가득 차면 인게임 보관함으로 보낸다.
- **저장 방식:** 단순 바닐라 아이템(메타 없음)은 정의별 수량으로 합산한다. 인챈트·이름·내구도 등 메타가 있는 아이템은 개체 행으로 두고 직렬화한 데이터를 보관해 꺼낼 때 그대로 복원한다. INAZINA 아이템은 기존 개체 행 규칙을 따른다.
- **제한(제안):** 서버 규칙으로 얻을 수 없는 아이템(기반암, 커맨드 블록, 스포너, 배리어 등)은 올릴 수 없다. 셜커 상자·가방처럼 내용물을 가진 아이템은 초기에는 올릴 수 없다.
- **남용 방지:** 복제 버그로 만든 아이템이 경제로 흘러들지 않도록 일일 업로드 상한, 급증 탐지, 관리자 로그를 둔다.

### 희귀도와 실시간 가격

**희귀도**
- 등급(제안): 일반 / 고급 / 희귀 / 영웅 / 전설. 등급 이름과 수는 설정값이다.
- 정의별로 지정한다. 바닐라 아이템은 획득 난이도와 유통량을 기준으로 기본 표를 만들고 관리자가 조정한다.
- 개체 단위 보정: 인챈트, 내구도, 강화 단계가 희귀도와 가격에 반영된다.

**실시간 가격(제안)**
- 가격 = 기준가(희귀도와 정의별 기준) × 수급 계수. 수급 계수는 웹 보관량, 최근 순업로드/순인출, 중고거래 최근 체결가로 정한다.
- 순업로드가 늘면 하락하고 순인출이 늘면 상승한다. 기준가 대비 상하한을 둔다.
- 갱신 주기는 경제 시간 기준이며, 시장 사건 엔진과 연결해 이벤트로 흔들 수 있다.
- 가격은 기준통화로 저장하고 표시할 때 환율로 환산한다.
- 쓰임: 지갑 자산 평가, 중고거래 가이드 가격, 세금 과표, 사망 시 손실 가치 표시.

**경고: 바닐라 아이템 가격은 통화 발행 경로가 될 수 있다.** 채굴·농사로 얻은 바닐라 아이템을 웹에 올려 시세로 팔 수 있으면 사실상 INAZINA 통화를 만드는 것이다. 즉시 매입(NPC 매입)은 기본적으로 두지 않고, 중고거래(사용자 간)로만 현금화하는 것을 권장한다. NPC 매입을 둔다면 결정 13번의 상한과 재원 규칙이 필요하다.

### 플러그인 DB 권한 (확정: 읽기 자유, 수정은 제한된 역할)

- **읽기:** 플러그인 전용 읽기 계정으로 필요한 테이블/뷰를 직접 읽는다. 시세, 잔액, 아이템, 알림 조회가 해당한다.
- **수정:** 제한된 DB 역할이 허용된 동작만 실행한다. 테이블에 직접 `INSERT/UPDATE`를 열지 않고, 저장 프로시저(함수)와 명령 큐 테이블에 대한 `INSERT`만 허용한다.
- **직접 수정을 허용하는 동작(프로시저):** 아이템 `location` 전환, 사망 소멸, 인벤토리 대조 결과 반영, 출석 체크 같은 단순하고 불변식이 명확한 동작.
- **명령 큐로 처리하는 동작:** 주문, 환전, 송금, 대출, 구매처럼 공통 전기·세금·원장 대사가 필요한 동작은 플러그인이 명령 큐에 요청을 넣고, INAZINA 서비스가 기존 매니저 코드로 실행한 뒤 결과를 돌려 준다. 이렇게 하면 "웹과 같은 기능"을 쓰면서도 원장 규칙을 우회하지 않는다.
- **불변식 강제:** 트리거로 소유권 중복, 음수 수량, 허용되지 않은 `location` 전환을 DB 수준에서 막는다. 역할 단위로 감사 로그를 남긴다.
- **주의:** 매니저 로직을 저장 프로시저로 복제하면 두 구현이 어긋난다. 복잡한 금융 동작은 SQL로 다시 만들지 말고 명령 큐를 쓴다.

### 통신 구조

- 플러그인 → INAZINA API(`apps/api`)는 서버 전용 키와 서명으로 인증한다. 키는 서버 단위로 발급·폐기한다.
- 기본은 플러그인이 일정 주기로 큐를 폴링하는 방식이다. 즉시성이 필요해지면 웹훅이나 소켓을 추가한다.
- 요청 형식은 버전 필드를 두어 플러그인과 API를 독립적으로 배포할 수 있게 한다.
- 사망, 드롭, 월드 이동 같은 인게임 사건은 INAZINA 경제에 직접 반영하지 않고 이벤트로 기록만 한다. 반영은 별도 정책 결정 후에 한다.

### 강화와 연동

- 강화는 웹/디스코드/인게임 어디서 시작해도 같은 INAZINA API 한 곳을 거친다.
- 아이템이 인게임에 있는 상태에서 강화하려면 먼저 회수 대기를 거치거나, 인게임에서 "강화 요청"을 보낼 때 아이템을 에스크로로 옮긴다. 결과는 같은 상태 기계로 돌려받는다.
- 단계별 능력치는 `mc_attributes`로 표현한다. 능력치 수치를 코드에 박지 않고 정의 데이터로 둬서 밸런스를 서버 재배포 없이 조정한다.
- 파괴 요소를 넣는다면 인게임 아이템 제거와 INAZINA 소멸 기록이 함께 일어나야 한다.

### 경제 영향과 균형

- 인게임 능력치 아이템은 서버 안의 플레이 균형까지 건드린다. 강화 효과 범위는 "수집/과시" 쪽에서 시작해 확인 후 넓히는 것을 권장한다.
- 마인크래프트 쪽 획득 경로(몹 드롭, 채굴)와 별개로, INAZINA 경제의 아이템 총량 상한은 유지한다.
- 인게임 재화를 INAZINA 통화로 바꾸는 연동은 이 기획 범위 밖이다. 별도 승인 후 다룬다.

### 단계

| 단계 | 내용 |
|---|---|
| 준비 | 아이템 정의와 개체 테이블에 mc 필드 확보, 전달 큐와 상태 기계 설계 (아이템 시스템 구현 때 같이) |
| 연동 1 | 계정 연결(`/link`), 전달 큐, 플러그인 폴링, 단방향 지급(웹 → 인게임) |
| 연동 2 | 회수(인게임 → 웹), 위조 검증, 관리자 모니터링 |
| 연동 3 | 인게임 강화 창구, 능력치 속성 적용 |
| 연동 4 | 뽑기·쇼핑몰 인게임 노출, 이벤트 기록 활용 |

## 전 시스템 연동 구상

INAZINA의 모든 시스템을 마인크래프트 서버와 연동할 예정이다. 구현은 소비처와 아이템 시스템 이후이며, 지금은 **연동 가능한 구조로 만드는 것**과 **연동 지도**를 확보하는 것이 목표다.

### 공통 기반

- **계정 연동:** 인게임 `/link` 일회용 코드 → HTS/디스코드에서 입력. 계정 하나에 UUID 하나. 정식(온라인 모드) 서버 전제.
- **서비스 계층:** 디스코드 봇, HTS/API, 마인크래프트 플러그인이 같은 도메인 로직(`managers/`)을 거친다. 플러그인은 DB 읽기는 직접 하고, 수정은 제한된 역할(저장 프로시저 + 명령 큐)로 하며, 명령 큐 요청은 INAZINA 서비스가 `managers/` 코드로 실행한다.
- **권한:** 인게임 명령과 GUI는 웹과 같은 권한 규칙(등록 여부, 정지·파산 상태, 거래 시간)을 적용한다.
- **알림:** 벨과 디스코드 DM에 인게임 채널(채팅, 액션바, 타이틀)을 추가한다. 접속 중이 아니면 접속 시 모아서 보여 준다.
- **성능:** DB·API 호출은 항상 비동기로 한다. 서버 메인 스레드에서 DB를 기다리지 않는다. 자주 쓰는 값(잔액, 시세)은 짧게 캐시한다.
- **표시:** 통화 소수 자릿수와 단위는 INAZINA의 통화 설정(`currency_config`)을 그대로 따른다.
- **장애 시:** 마인크래프트 서버가 꺼져도 INAZINA는 정상 동작한다. API/DB가 끊기면 인게임은 읽기 전용 안내 메시지로 전환하고 경제 행위를 막는다.

### 인게임 행위가 경제에 미치는 영향 (정책 결정 필요)

- 인게임 채굴·몹 드롭·농사 등으로 INAZINA 통화를 직접 만들지 않는다. 필요하면 NPC 법인이 정해진 단가로 사들이는 구조(국고/법인 재원)로 하고 일일 상한을 둔다.
- 인게임 상점 거래도 쇼핑몰과 같은 소비 엔진을 거쳐 세금과 원장에 전기한다. 인게임 전용 장부를 따로 만들지 않는다.
- 인게임 PvP·사망 손실이 경제에 미치는 영향은 사망 시 아이템 소멸만 인정하고, 통화 손실은 만들지 않는다. (결정 필요)
- 소비로 인한 파산은 허용하고 구매 한도는 두지 않는다(웹 쪽 확정). 인게임 구매도 같은 규칙이며, 파산 단계에서의 인게임 경제 행위 제한은 연동 지도의 "신용점수·파산" 항목을 따른다.
- 인게임 직접 거래로 중고거래 세금과 수수료를 회피하지 못하게, 소유권 이전은 모두 웹 거래와 같은 경로를 거친다.

## 결정 사항

8. (확정) 마인크래프트 연동은 웹 ↔ 인게임 양방향, 같은 DB 공유.
9. (확정) 인게임 사망 시 아이템 소유권 소멸.
10. (확정) 서버는 Paper 기반.
11. (확정) 플러그인은 DB를 읽기만 자유롭게 하고, 수정은 제한된 역할로 허용된 동작만 한다. 세부 구현은 단순 동작은 저장 프로시저, 금융 동작은 명령 큐로 하는 것을 제안한다. (확인 필요)
12. (확정) 사망 시 사망한 자리에 유품상자(큰상자) 설치, 소유권은 소멸하고 재취득 가능. 세부는 18번.
12-1. (확정) 인게임 ↔ 웹 이동: 보내기를 고르면 출발지에서 제거되고 도착지에 지급. 인벤토리 인식으로 DB와 대조.
12-2. (확정) 인게임에서도 웹과 같은 기능 제공.
13. 마인크래프트: 인게임 채굴·드롭을 INAZINA 경제로 바꾸는 NPC 매입 구조를 허용할지.
14. 마인크래프트: 인게임 주식·옵션·선물 주문을 허용할 범위. (권장: 조회와 간단 주문만, 복잡한 상품은 웹)
15. (확정) INAZINA 시스템 시간 단위는 앞으로 마인크래프트 서버 내 시간. 미정: 경제 시계 방식(권장)과 서버 틱 합산 방식 중 선택, 환산 비율(1일=20분 유지 여부), 진행 중인 계약의 전환 규칙, 서버 정지 중 금융 시간을 멈출지.
16. (확정) 거주지는 서버 안에서 설정한다. 미정: 설정 방식(침대, 명령, 소유 필지 중), 변경 대기 기간(세금 회피 방지), 국가별 구역과의 관계.
17. 중고거래: 인게임 직접 교환을 허용할지, 허용한다면 웹 거래와 같은 경로를 어떻게 강제할지. 드롭 줍기 규칙(결정 12)과 함께 정한다.
18. 유품상자 세부: 담기는 대상이 INAZINA 아이템만인지 바닐라 아이템 포함인지(제안: 소지품 전부 담고, 소유권은 INAZINA 아이템만 해당). 사망자 우선 수령 시간을 둘지, 처음부터 누구나 가능한지. 유품상자 유지 시간과 만료 후 처리(제안: 만료 시 내용물을 국고 귀속). 상자가 파괴됐을 때 내용물 처리. 사망 보호 소모품을 둘지.
19. 웹 보관함: 바닐라 아이템 올리기 허용 목록과 금지 목록, 메타 아이템(인챈트, 책, 셜커 상자) 허용 범위, 일일 업로드 상한.
20. 희귀도와 가격: 희귀도 등급 이름과 수, 바닐라 아이템 기본 희귀도 기준, 가격 모델(수급 계수, 상하한, 갱신 주기). 바닐라 아이템의 NPC 즉시 매입을 둘지(권장: 두지 않고 중고거래로만 현금화, 결정 13번과 함께).
